# ReadAside 可追溯上下文引擎实施路线图

> 路线状态：`approved`
>
> 项目状态：`active · beta`
>
> 规划起点：`0.8.0`
>
> 最后更新：2026-08-26
>
> 主叙事：AI / Agent 应用工程
> 技术亮点：Agent Infra 式上下文编排、可观测轨迹与离线评测
> 实施状态：`M1` 与 `M2` 可见核心切片已完成，下一门槛为 `M0` 评测基线

## 1. 一句话目标

把 ReadAside 从“把整页文字交给模型的浏览器侧栏”，升级为一个能够**结构化理解网页、选择真正相关的上下文、要求回答引用证据，并把证据定位回网页原文**的本地阅读系统。

核心闭环：

```text
网页内容
   ↓ 结构化采集
可定位内容块
   ↓ 本地检索与上下文预算
本次真正发送的证据
   ↓ 带引用的模型回答
经过校验的证据卡片
   ↓ 点击定位
网页原文高亮
```

这个闭环既直接改善个人阅读体验，也让项目具备可以在简历中展示的完整技术主线：浏览器内容工程、检索与上下文编排、模型输出约束、证据回链以及量化评测。

## 2. 问题定义（Problem）

M2 之前，模型输入是一段最长 80,000 字符的扁平文本。当前已经可以在本地选择相关内容块，但仍需通过评测确认选择质量，并继续解决回答核验和原文回链问题：

1. **上下文浪费**：多数问题只依赖页面中的少量段落，整页发送增加延迟、费用和噪声。
2. **页面结构丢失**：标题层级、正文段落、列表、代码和所在 frame 等信息在合并后被弱化。
3. **回答难以核验**：模型可以生成看似合理的回答，但用户不知道具体依据来自哪里。
4. **无法可靠回到原文**：即使回答给出一句引用，重复文字、iframe、Shadow DOM 和页面变化也可能导致错误定位。

真正要解决的不是“再加一个聊天框功能”，而是建立一条可检查、可评测、可回退的网页上下文流水线。

## 3. 目标用户与预期价值

### 3.1 目标用户

第一阶段仍然服务本地个人用户，重点场景包括：

- 阅读技术博客、产品文档和长文章。
- 检查 CI 日志、代码说明和复杂网页文本。
- 针对一段选区追问定义、原因、上下文或相关结论。
- 希望知道 AI 读到了什么、为什么这样回答的人。

### 3.2 为什么现在值得做

`0.8.0` 已经打通权限、页面提取、选区、流式问答、搜索引用、错误诊断和手动重试。当前主要瓶颈已经从基础可用性转移到上下文质量与回答可信度，适合在不重写产品的前提下升级核心链路。

### 3.3 预期价值

- 用更少的页面文字得到质量不下降、最好更准确的回答。
- 发送前能看到模型将依据哪些内容，而不只是一个字符总数。
- 回答中的网页依据必须对应真实内容块，不能凭空生成引用编号。
- 点击依据可以尽可能回到正确的 frame、Shadow DOM 或普通正文位置。
- 每次检索为何选中或排除某段内容都能在本地诊断中解释。

## 4. 核心痛点（Pain Points）

| 痛点 | 当前表现 | 目标表现 |
| --- | --- | --- |
| 输入粒度过粗 | 页面被合并成一段长文本 | 标题、段落、列表、代码等成为独立内容块 |
| 选区上下文过大 | 选区与整页同时发送 | 固定选区，并按问题补充邻近或相关块 |
| 模型依据不透明 | 只能阅读回答文本 | 回答引用本次发送的块编号 |
| 引用可能失真 | 无本地校验 | 未知编号、错误摘录和失效位置明确标记 |
| 定位不稳定 | 只能全文搜索短句 | frame、Shadow 路径、结构路径和文本锚点组合定位 |
| 缺少效果证据 | 主要依赖主观试用 | 固定数据集、基线、指标和回归报告 |

## 5. 现有替代方案（Existing Alternatives）

| 方案 | 优点 | 仍未解决的问题 |
| --- | --- | --- |
| 复制网页到通用聊天工具 | 简单、模型选择多 | 打断阅读，来源结构和原文位置丢失 |
| 通用浏览器 AI 侧栏 | 开箱即用 | 上下文选择通常不可检查，隐私和失败原因不透明 |
| 全文 RAG / 向量检索 | 适合大规模资料 | 对单页阅读偏重，需要索引、存储或额外模型 |
| 浏览器查找原文 | 精确匹配简单 | 无法处理改写引用、重复文本和跨文档层定位 |

ReadAside 的差异化不是模型更多，而是把“采集—检索—发送—引用—定位”做成一个本地、透明、可验证的闭环。

## 6. 可创新切入点（Differentiation）

### 6.1 结构感知的网页内容块

不再只返回 `page.text`，而是同时生成内容块。每个块保留：

- 块编号和页面内顺序。
- 内容类型，例如标题、段落、列表项、表格、代码或输入区域。
- 标题路径，例如 `模型架构 > Attention`。
- 所在顶层页面、iframe 或开放式 Shadow DOM。
- 用于重新查找原文的组合锚点。

### 6.2 本地混合检索与上下文预算

第一版不引入服务器、向量数据库或额外 Embedding API，而是在扩展本地使用：

- 中文字符片段与英文单词的词法匹配。
- 标题、选区、代码和邻近段落加权。
- 相邻块扩展，避免只截取孤立句子。
- 重复内容抑制，避免导航栏和模板文本占满预算。
- 明确的字符预算器，记录候选、得分、选中和排除原因。

这一方案足以验证核心价值，也保留未来增加语义重排器的接口。

### 6.3 可验证引用，而不只是提示模型“给来源”

模型只能引用本次实际发送的块编号，例如 `[B0001]`。扩展收到回答后执行本地校验：

- 引用编号是否存在。
- 对应内容块是否确实发送给模型。
- 若回答同时返回原文摘录，摘录是否能在对应块中找到。
- 无效引用不伪装成可点击证据。

### 6.4 证据回链与降级策略

定位不依赖单一 CSS Selector，而是按以下顺序尝试：

1. frame 与开放式 Shadow DOM 路径。
2. 捕获时保存的结构路径。
3. `exact + prefix + suffix` 文本锚点。
4. 当前文档层内的候选文本匹配。
5. 无法唯一定位时只展示证据卡片并说明失效，不错误跳转。

### 6.5 面向 Agent Infra 的本地检索轨迹

每次请求生成一份只存在于当前侧栏内存的 `RetrievalTrace`，用于解释：

- 问题采用了哪种上下文模式。
- 一共发现多少内容块。
- 哪些块被固定、检索、邻近扩展或去重。
- 字符预算怎样分配。
- 检索与组装分别耗时多久。

默认只展示简洁发送预览，高级诊断按需展开；不上传轨迹、不建设遥测服务。

## 7. 目标架构地图

```text
Chrome 当前标签页
  ├─ 顶层 Document
  ├─ 可访问 iframe
  └─ 开放式 Shadow DOM
            │
            ▼
  [1] Block Extractor
      可见性判断 · 结构识别 · 去重 · 组合锚点
            │
            ▼
      PageDocument + ContentBlock[]
            │
       ┌────┴──────────────┐
       ▼                   ▼
  [2] Local Index     [3] Selection Pin
  词法特征/标题权重       固定选区及邻近块
       └────┬──────────────┘
            ▼
  [4] Retriever + Context Budgeter
      候选召回 · 排序 · 邻块扩展 · 去重 · 截断
            │
            ├──────────────► RetrievalTrace（仅本地内存）
            ▼
  [5] Prompt Builder
      带块编号的有限上下文 + 引用输出契约
            │
            ▼
       DeepSeek API
            │
            ▼
  [6] Citation Parser + Validator
      引用编号校验 · 摘录校验 · 失效降级
            │
       ┌────┴──────────────┐
       ▼                   ▼
  回答与证据卡片       [7] Evidence Resolver
                           定位 · 滚动 · 临时高亮
```

模块边界必须保持单向：提取模块不依赖模型，检索模块不操作页面，引用解析不直接操作 DOM，定位失败不能影响回答正常展示。

## 8. 核心数据契约草案

这些字段用于明确模块边界，具体命名可在实现前通过测试夹具微调。

```js
PageDocument {
  schemaVersion,
  captureId,
  title,
  url,
  capturedAt,
  blocks: ContentBlock[],
  diagnostics
}

ContentBlock {
  id,                 // 仅在本次 capture 内稳定，例如 B012
  order,
  kind,               // heading | paragraph | list | table | code | input | other
  text,
  headingPath: [],
  source: {
    frameId,
    frameLabel,
    shadowDepth
  },
  locator: {
    structurePath,
    shadowPath: [],
    textQuote: { exact, prefix, suffix }
  }
}

RetrievalTrace {
  traceId,
  captureId,
  query,
  mode,
  budgets,
  candidates: [],
  selected: [],
  excluded: [],
  timings
}
```

约束：

- `block.id` 不承诺跨刷新稳定，避免制造不存在的长期身份语义。
- `locator` 是多种定位信号的组合，不把 CSS Selector 当作唯一真相。
- 第一版继续使用字符数预算，不展示伪精确 Token 数；后续有可靠 tokenizer 时再升级。
- 页面正文继续保留为兼容字段，直到新链路通过回归测试并可安全切回全文模式。

## 9. MVP 边界（In / Out）

### 9.1 本轮主线包含

- 普通网页、本地 HTML/TXT/JSON/Markdown 的结构化内容块。
- 顶层页面、可访问 iframe 和开放式 Shadow DOM 的来源信息。
- `自动 / 仅选区 / 结合全文` 三种上下文模式。
- 本地词法检索、邻近块扩展、去重和字符预算。
- 发送前的内容块预览和检索诊断。
- 回答中的块级引用、证据卡片和本地有效性校验。
- 普通 DOM、可访问 iframe、开放式 Shadow DOM 的原文定位与临时高亮。
- 固定测试夹具、离线问题集和指标报告。

### 9.2 明确暂不包含

- 向量数据库、远程索引、云端账号和同步。
- 第二模型或外部 Embedding 服务。
- PDF、图片理解、Canvas OCR 和关闭式 Shadow DOM。
- 自动滚动并抓取完整虚拟列表。
- 跨页面知识库、长期记忆和自主网页操作 Agent。
- 为提高指标而上传真实私密网页、问题或检索轨迹。

## 11. 分阶段实施步骤

### M0：建立基线和验收契约

**目标**：先证明后续改动到底改善了什么，避免只凭演示观感判断。

步骤：

1. 建立不含隐私数据的 HTML 测试页，覆盖长文章、技术文档、重复导航、代码块、表格、iframe 和开放式 Shadow DOM。
2. 选择 3 个公开真实网页做人工试用记录，不把页面全文提交到仓库。
3. 准备最小评测集：至少 30 个问题，并标注回答所需的证据段落。
4. 记录当前全文模式的发送字符数、首字等待时间和答案是否命中证据。
5. 固定指标计算方式和报告模板。

**完成标准**：

- 测试夹具能够稳定复现，不依赖易变化的线上页面。
- 每个问题至少有一个人工标注的证据块或明确标记为页面无法回答。
- 当前 `0.9.0` 保留的全文输入结果被保存为基线，而不是日后凭印象比较。

**本阶段不做**：生产提取逻辑改造和 UI 变化。

**当前进展（2026-09-01）**：M0 的确定性部分已完成技术文档、长文章和复杂 DOM 共 3 个夹具、30 题与 32 个必需证据块。调整前 `0.9.1` 的证据召回为 100%、缩减中位数为 46%；收敛候选和邻块规则后，`0.9.2` 的证据召回保持 100%（32/32），缩减中位数达到 76%，自动全文回退为 0/30，2,000 块压力测试低于 100 ms 门槛。详细对比见 [`docs/evaluation/retrieval-baseline-0.9.1.md`](./evaluation/retrieval-baseline-0.9.1.md) 和 [`docs/evaluation/evaluation-0.9.2.md`](./evaluation/evaluation-0.9.2.md)。公开真实网页与模型回答质量仍留给人工验收，不混入确定性指标。

### M1：结构化采集与兼容预览（`0.9.0`，已完成）

**目标**：从扁平字符串升级为 `PageDocument + ContentBlock[]`，但暂不改变默认模型输入。

步骤：

1. 定义并测试 `PageDocument`、`ContentBlock` 和 locator schema。
2. 在每个可访问文档层识别标题、段落、列表、表格、代码和输入内容。
3. 保存标题路径、文档层来源、页面内顺序和文本锚点。
4. 为重复导航、隐藏元素、空块和过小碎片制定合并/排除规则。
5. 由内容块重新生成兼容的 `page.text`，与当前模型契约并行存在。
6. 在预览诊断中增加内容块数量和类型统计，但默认请求仍发送全文。
7. 补齐 iframe、Shadow DOM、本地文件和 80,000 字符保护的回归测试。

**完成标准**：

- 现有读取和问答行为不变。
- 结构化内容可序列化通过 Chrome 消息边界。
- 内容块重新拼接后不丢失当前可见正文。
- 每个可引用块都有唯一的 capture 内编号和可解释来源。

**回退方式**：忽略 `blocks`，继续使用现有 `page.text`。

**完成结果**：已生成 `readaside/page-document/v1`，支持通用网页和本地 Markdown/JSON 的类型化内容块、标题路径、frame/开放式 Shadow DOM 来源、组合 locator、跨 frame 统一编号、独立 80,000 字符保护以及侧栏数量/类型诊断。M1 完成时模型输入仍沿用 `page.text`，随后由 M2 自动模式接入块级上下文。

### M2：本地检索、上下文预算与发送预览（核心切片已完成）

**目标**：在默认 `自动` 模式下只发送与问题相关的内容，同时让用户看到选择结果。

步骤：

1. 为中文建立字符片段特征，为英文和代码建立单词/符号特征。
2. 实现标题匹配、正文匹配、选区固定、内容类型和位置等可解释评分。
3. 加入邻近块扩展，保留定义所在标题和前后语境。
4. 加入重复抑制和字符预算器；预算不足时优先保留选区和高分证据。
5. 生成 `RetrievalTrace`，记录候选得分、选中理由、排除理由和耗时。
6. 提供上下文模式：
   - `自动`：选区固定 + 问题相关块 + 必要邻块。
   - `仅选区`：只发送选区及可配置的最小结构信息。
   - `结合全文`：保持现有行为，用于兼容和排查。
7. 发送前展示模式、块数、字符数和将发送的证据预览。
8. 对 30 个基线问题运行新旧对比，不满足指标时保持全文为默认。

**完成标准**：

- 自动模式的发送字符数中位数比全文基线下降至少 60%。
- 人工标注证据的 `Recall@K` 不低于 85%。
- 2,000 个内容块规模下，本地检索与预算组装的 p95 目标低于 100 ms。
- 用户可以一键切回结合全文，切换不会污染页面或对话状态。

**回退方式**：将上下文模式设为 `结合全文`，不删除结构化采集结果。

**当前完成结果**：

- 使用中文字符片段和英文/代码词法特征进行本地评分。
- 当前选区获得最高优先级；普通问题最多采用两个词法种子，复合问题按分句分配种子，并补充所属标题与同文档层、同标题路径的一个正文邻块。
- 短追问同时参考最近两条用户问题，避免“为什么”等问法丢失主题。
- 自动模式最多组装 16,000 字符；2,000 字符以内的短页面保留全文。
- 输入问题后实时展示采用块、采用原因、发送字符数和缩减比例。
- 提供“自动选择 / 结合全文”两种模式；暂不单设“仅选区”，因为选区已经在自动模式固定并作为独立高优先级内容发送。
- 当前轨迹记录查询特征、候选数量、选中块、字符预算和块数预算；完整候选得分/排除原因与固定数据集评测留给 M0 补齐。

### M3：块级引用、校验与证据卡片（`0.10.0`，已完成）

**目标**：回答结论能够对应本次发送的网页证据。

步骤：

1. Prompt Builder 使用稳定格式发送块编号、标题路径和文本。
2. 要求模型对来自当前网页的关键事实使用 `[B0001]` 格式引用。
3. 明确区分网页证据与 DeepSeek Web Search 的外部来源，避免编号混用。
4. Citation Parser 从 Markdown 中解析块引用，不破坏代码块、链接和脚注。
5. Validator 检查编号存在性、是否已发送以及可选摘录是否属于对应块。
6. 在回答下方展示证据卡片：标题路径、短摘录、来源文档层和有效状态。
7. 无效引用显示为不可点击并说明原因；不能静默链接到相似但错误的段落。
8. 增加提示词注入测试：网页中的“忽略指令”等文本不得改变引用协议或系统行为。

**完成标准**：

- 所有可点击块引用都来自本次实际发送的集合。
- 固定评测集中无效块编号比例不高于 5%。
- 没有引用时回答仍能正常展示，不因解析失败丢失正文。
- 页面引用和 Web Search 引用在视觉与数据结构上可区分。

**回退方式**：关闭证据增强渲染，仅显示原始 Markdown 回答。

**完成结果**：自动检索请求使用 `readaside/block-citation/v1` 和允许块号白名单；解析器忽略代码和链接，校验器只接受发送时证据快照中的编号，并区分“页面存在但未发送”与“页面中不存在”。有效标记跳到同一回答下方的证据卡片，无效标记不可点击；DeepSeek Web Search 来源继续作为外部链接或数字脚注展示。固定 8 个引用用例全部通过，3 个无效引用全部被拦截且错误放行为 0。当前 v1 只验证块号，不要求模型返回独立原文摘录；“结合全文”因为没有块头而保持无引用兼容路径。真实模型的引用覆盖和证据支持关系继续由人工验收记录。

### M4：原文定位、滚动与临时高亮

**目标**：点击证据卡片后，尽可能回到正确网页位置；失败时诚实降级。

步骤：

1. 实现独立 `EvidenceResolver`，接收 locator 而不是重新执行全文提取。
2. 先支持普通顶层 DOM 的文本锚点定位和滚动。
3. 增加可访问 iframe 的 frame 路由。
4. 增加开放式 Shadow DOM 的 shadow path 解析。
5. 对重复文本使用 prefix、suffix、标题路径和文档层共同消歧。
6. 使用扩展自有样式进行短暂高亮，避免永久修改页面内容。
7. 页面已经变化或目标不可访问时返回结构化失败原因。
8. 增加重排、重复段落、iframe、Shadow DOM 和节点被替换后的回归测试。

**完成标准**：

- 静态测试页中 top-1 定位成功率目标不低于 90%。
- 重复文本不会默认跳到第一个错误结果。
- 定位失败不影响回答和证据卡片阅读。
- 高亮可以自动消失或被下一次定位替换，不残留页面状态。

**回退方式**：证据卡片继续可读，但隐藏“定位原文”操作。

### M5：扩大评测、产品收口与候选发布

**目标**：把技术能力变成可复现、可展示、可写进简历的项目证据。

步骤：

1. 将评测集扩展到至少 100 个问题，覆盖文章、文档、日志、代码、表格和复杂 DOM。
2. 输出全文基线与自动上下文的对比报告：发送量、证据召回、引用有效率、定位成功率和本地耗时。
3. 执行隐私与权限复查，确认没有新增常驻读取、远程日志或宽泛权限。
4. 制作 60—90 秒演示：提问 → 查看发送证据 → 阅读带引用回答 → 点击回到原文。
5. 更新 README 架构图、真实指标、限制说明和版本迁移说明。
6. 在干净 Chrome Profile 中完成普通网页、本地文件、复杂 DOM、断联和失败恢复验收。
7. 生成候选发布包；满足全部门槛后再统一决定下一版本号。

**完成标准**：

- 所有公开指标都能由仓库中的测试或报告复现。
- README 不使用尚未验证的准确率或性能数字。
- 演示展示真实扩展流程，不使用静态假界面替代核心能力。
- `npm run verify` 和发布包检查全部通过。

## 13. 测试地图

| 层级 | 重点测试 | 典型风险 |
| --- | --- | --- |
| 单元测试 | 分块、特征、评分、预算、引用解析、locator | 边界输入和规则回归 |
| 夹具集成测试 | iframe、Shadow DOM、重复文本、代码和表格 | 文档层与定位错配 |
| 模型契约测试 | 已知编号、未知编号、无引用、Web Search 引用 | Markdown 与引用语法冲突 |
| 性能测试 | 500 / 1,000 / 2,000 块 | 侧栏卡顿和重复计算 |
| 隐私测试 | Key、页面内容、轨迹生命周期 | 意外持久化或日志泄露 |
| 人工验收 | 公开真实网页和本地文件 | 测试夹具过于理想化 |

模型结果存在波动，因此评测需要区分：

- **确定性指标**：分块、检索集合、字符数、引用合法性、定位结果和本地耗时。
- **人工判断指标**：回答是否完整、是否误解页面、自动上下文与全文回答是否等价。

第一阶段优先把确定性指标做扎实，不用单次模型回答宣称系统准确率。

## 14. 主要风险与控制方式

### 风险 1：分块规则适配不完所有网站

- 使用语义标签、可见性和文本密度等通用信号，不维护站点名单。
- 对无法识别的内容保留 `other` 块，不因分类失败丢弃正文。
- `page.text` 兼容链路保留到新路径稳定。

### 风险 2：词法检索不理解同义表达

- 第一版用标题、邻近关系和选区固定弥补。
- 通过失败案例决定是否增加可插拔语义重排，而不是预先接入新 API。

### 风险 3：要求引用可能影响回答流畅度

- 只要求关键网页事实带引用，不要求每句话都引用。
- 引用解析与正文渲染解耦，解析失败不隐藏回答。

### 风险 4：页面变化导致 locator 失效

- 使用多信号匹配并返回置信状态。
- 宁可说明“原文位置已变化”，也不跳转到错误段落。

### 风险 5：路线过大，长期没有可用版本

- 每个里程碑单独发布和验收。
- M1 只改数据层，M2 才改变默认上下文，M3/M4 分开交付。
- 一个阶段未达到门槛时不并行扩展下一个核心能力。

## 15. 预计代码落点

以下只是模块边界规划，不要求一次创建完毕：

```text
lib/
  page-document.mjs       # schema、兼容转换和基本校验
  content-blocks.mjs      # 分块、标题路径和块级清理
  text-features.mjs       # 中英文/代码词法特征
  context-retriever.mjs   # 候选召回、评分和邻块扩展
  context-budgeter.mjs    # 字符预算、去重和截断
  retrieval-trace.mjs     # 本地可解释轨迹
  citation-parser.mjs     # 块引用解析与合法性校验
  evidence-locator.mjs    # locator 生成与解析的纯逻辑

test/
  fixtures/context/       # 不含隐私数据的固定复杂页面
  evaluation/             # 问题、证据标注和指标脚本

docs/
  evaluation/             # 基线、版本对比和方法说明
```

页面 DOM 操作仍由注入函数完成；能写成纯函数的分块、检索、预算和引用校验都放在 `lib/`，以便快速、稳定地测试。

## 16. 实施时的决策门

以下节点需要先看数据再决定，不在本路线图中提前锁死：

1. **自动模式是否成为默认**：只有 M2 达到证据召回和上下文缩减门槛后才切换。
2. **是否加入语义重排**：只有词法检索在固定失败集上持续不足，且收益大于隐私、费用和复杂度时再评估。
3. **是否持久化检索轨迹**：默认不持久化；未来若为了回放评测保存，必须先定义清理和脱敏语义。
4. **是否进入 1.0**：由真实使用稳定性、评测完整度和开源文档质量决定，不只看功能数量。
