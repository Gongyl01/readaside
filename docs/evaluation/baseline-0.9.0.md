# ReadAside `0.9.0` 上下文评测基线

> 日期：2026-08-28
>
> 阶段：M0-A 试点
> 性质：离线、确定性评测，不调用 DeepSeek

## 结论

当前技术文档夹具的证据召回为 **100%（10/10）**，说明 10 个问题所需的证据块都进入了自动上下文；上下文缩减比例中位数为 **42%**，没有达到路线图设定的 **60%** 门槛。因此，本轮只能证明评测链路可用以及当前检索在该夹具上没有漏证据，不能据此宣布自动上下文已经达到最终效率目标，也不应直接用这组数字作为公开效果结论。

## 范围

- 固定夹具：[technical-doc.html](../../test/fixtures/context/technical-doc.html)
- 结构化夹具：[technical-doc.json](../../test/fixtures/context/technical-doc.json)
- 问题与证据标注：[technical-doc.questions.json](../../test/evaluation/technical-doc.questions.json)
- 评测命令：`npm run evaluate:context`
- 门槛检查：`npm run evaluate:context:gate`（当前会因缩减不足而失败）
- 问题数量：10
- 页面规模：2,650 个兼容文本字符、24 个结构化内容块
- 覆盖结构：长正文、标题路径、导航噪声、代码、列表、引用和原生表格

本试点不抓取或提交真实网页，不调用模型，不评估回答质量、首字等待时间和真实网站提取兼容性。HTML 用于保留可人工查看的页面形态；离线脚本在等价的 `PageDocument` 契约夹具上评测当前检索与预算逻辑，因此本报告测量的是“证据是否被选中”和“本地组装减少了多少字符”，不是端到端模型准确率。

## 标注与计算方法

每道题保存一到多条必须命中的唯一证据原文。评测脚本先在结构化内容块中将证据原文解析为当前 capture 的 `Bxxxx`，再调用生产代码中的 `buildContextPlan()`：

1. `Recall@K`：被自动上下文选中的必需证据块数 ÷ 全部必需证据块数。
2. 上下文缩减：`1 - 自动上下文字符数 ÷ 完整兼容文本字符数`。
3. 全文回退：自动模式是否因为短页面、缺少内容块或无法安全选择而发送全文。
4. 本地耗时：每题重复运行 30 次检索与组装，汇总 p95；该数字只用于发现明显性能回退，不跨机器比较。

证据使用原文片段而不是硬编码块编号，避免在夹具前方插入内容后所有标注失效。每条证据必须且只能命中一个内容块，歧义或缺失会让评测命令直接失败。

## 汇总结果

| 指标 | 当前结果 | 目标 | 状态 |
| --- | ---: | ---: | --- |
| 证据召回 `Recall@K` | 100%（10/10） | ≥ 85% | 通过 |
| 上下文缩减中位数 | 42% | ≥ 60% | 未通过 |
| 自动回退全文 | 0/10 | 仅安全回退 | 正常 |
| 本地检索与组装 p95 | < 1 ms | < 100 ms（2,000 块目标） | 当前规模通过 |

性能结果来自本机重复运行，具体数值会随机器负载变化；24 块夹具不能替代路线图要求的 2,000 块压力测试。常规 `npm run verify` 会验证评测集能够完整运行，但基线阶段不会因为尚未达到效果门槛而中断构建；需要显式执行 `npm run evaluate:context:gate` 才会把门槛作为退出状态。

## 初步观察

10 道题中有 7 道采用了块数上限允许的 10 个块，另外 3 道也采用了 8–9 个块。当前策略会先取最多 4 个词法命中，再为命中补充所属标题和前后块；在技术文档中，问题词与标题、指标名和排障段落交叉出现，扩展后的上下文很快接近块数上限。证据没有遗漏，但邻近扩展和多候选带来的冗余使字符缩减没有达到目标。

这一观察只来自一个虚构技术文档夹具，尚不足以据此调整生产检索规则。下一步应先补齐长文章和复杂 DOM 两类夹具，把评测扩展到 30 题；如果“高召回、低缩减”的模式仍然存在，再针对候选数量、邻块扩展和重复内容抑制进行小范围修正，然后重新运行同一评测集。
